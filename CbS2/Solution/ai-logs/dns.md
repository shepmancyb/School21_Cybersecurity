# AI-лог: разбор DNS (задание 3)

> Источник данных: реальный файл `dns.pcap`, захваченный в GNS3.
> Топология: R2 (10.0.0.2) — клиент, R1 (10.0.0.1) — DNS-сервер,
> my.site → 192.168.100.1 (Loopback0 на R1).

---

## 1. Разбор полей DNS-пакета с акцентом на кодирование имени

### DNS-запрос (Frame 4)

```
Ethernet:  src c4:02:77:bb:00:00 → dst c4:01:77:8f:00:00
IP:        src 10.0.0.2          → dst 10.0.0.1
UDP:       src port 57518        → dst port 53
DNS:
  Transaction ID : 0xa19e
  Flags          : 0x0100  (Standard query, RD=1)
  Questions      : 1
  Answer RRs     : 0
  Queries        : my.site  type A, class IN
```

### DNS-ответ (Frame 5)

```
Ethernet:  src c4:01:77:8f:00:00 → dst c4:02:77:bb:00:00
IP:        src 10.0.0.1          → dst 10.0.0.2
UDP:       src port 53           → dst port 57518
DNS:
  Transaction ID : 0xa19e        ← тот же, что в запросе
  Flags          : 0x8180  (Standard query response, No error, RA=1)
  Questions      : 1
  Answer RRs     : 1
  Queries        : my.site  type A, class IN
  Answers        : my.site  type A, class IN, TTL 10, addr 192.168.100.1
```

---

### Назначение ключевых полей

**Transaction ID (0xa19e)**
Случайное 16-битное число, которое R2 сгенерировал для этого запроса.
R1 обязан вернуть тот же ID в ответе — так клиент сопоставляет ответ
со своим запросом. Это же базовая защита от спуфинга: атакующий должен
угадать Transaction ID, чтобы подсунуть поддельный ответ раньше
настоящего сервера.

**Flags**
Набор битовых флагов:
- QR=0 в запросе (query), QR=1 в ответе (response)
- Opcode=0 — стандартный запрос
- RD=1 (Recursion Desired) — R2 просит R1 выполнить рекурсивное
  разрешение, если сам не знает ответа
- RA=1 в ответе (Recursion Available) — R1 сообщает, что поддерживает
  рекурсию
- RCODE=0 (No error) — имя успешно разрешено

**Questions: 1**
Счётчик вопросов в секции Queries. Клиент задаёт один вопрос:
«какой IPv4-адрес у my.site?»

**Answer RRs: 1**
Счётчик ресурсных записей в секции Answers. R1 вернул одну запись:
my.site → 192.168.100.1, TTL=10 секунд.

---

### Кодирование имени my.site в формате меток (label format)

DNS не передаёт имя как строку «my.site» — оно разбивается на метки,
каждой предшествует байт с длиной, имя завершается нулевым байтом:

```
Имя:   m  y  .  s  i  t  e
       ───────    ───────────
       метка 1    метка 2

Байты (hex):
  02  6D 79  04  73 69 74 65  00
  │   └─my─┘ │   └──site──┘  │
  │           │               └ терминатор (длина = 0, конец имени)
  │           └ длина метки "site" = 4
  └ длина метки "my" = 2
```

После имени идут:
- QTYPE  = 00 01  → A (Host Address)
- QCLASS = 00 01  → IN (Internet)

Такая структура позволяет DNS-парсеру читать имена любой вложенности
без поиска разделителей внутри данных.

## 2. Иерархия DNS: рекурсивный запрос www.google.com

Наш R1 авторитативен только для зоны `my.site`. Если с R2 попробовать
разрешить `www.google.com` через тот же R1, произойдёт следующее:

В нашей лабораторной среде (без выхода в интернет) R1 вернёт ошибку
NXDOMAIN или SERVFAIL — он не знает зону google.com и не имеет
доступа к корневым серверам.

Как выглядел бы реальный рекурсивный путь (если бы у R1 был интернет):

```
R2 (клиент)
  │  запрос: www.google.com? (RD=1)
  ▼
R1 (рекурсивный резолвер)
  │  не знает ответа → идёт к корневым серверам (.)
  ▼
Корневые серверы (13 кластеров, a.root-servers.net ... m.root-servers.net)
  │  «не знаю A-запись, но NS для .com — вот они»
  ▼
TLD-серверы .com (a.gtld-servers.net и др.)
  │  «не знаю A-запись, но NS для google.com — ns1.google.com»
  ▼
Авторитативные серверы google.com (ns1.google.com и др.)
  │  «www.google.com → 142.250.x.x»  (конкретный A-адрес)
  ▼
R1 кеширует ответ на время TTL и возвращает его R2
  ▼
R2 получает IP и отправляет ICMP/TCP туда
```

Ключевые понятия:
- **Корневые серверы** — знают только, кто отвечает за TLD (.com, .ru…)
- **TLD-серверы** — знают, кто отвечает за конкретный домен второго уровня
- **Авторитативный сервер** — хранит финальные записи зоны
- **Рекурсивный резолвер** — выполняет весь путь за клиента, кеширует
  результат по TTL записи

## 3. Три типа ресурсных записей DNS (кроме A)

### AAAA — адрес IPv6

Аналог записи A для 128-битных IPv6-адресов. Нужен, чтобы клиенты
с поддержкой IPv6 получали адрес назначения без необходимости
использовать IPv4.

Пример записи в зоне:
```
my.site.  3600  IN  AAAA  2001:db8::192:168:100:1
```
Ответ сервера на запрос AAAA:
```
Transaction ID: 0xb2c3
Flags: 0x8180 (response, no error)
Answers: 1
  my.site  type AAAA  class IN  TTL 3600
  Address: 2001:db8::192:168:100:1
```

---

### MX — почтовый сервер (Mail Exchanger)

Указывает, на какой сервер доставлять письма для домена. Содержит
приоритет (меньше = выше приоритет) и имя почтового сервера.

Пример записи:
```
my.site.  3600  IN  MX  10  mail.my.site.
```
Ответ сервера на запрос MX:
```
Transaction ID: 0xc3d4
Flags: 0x8180 (response, no error)
Answers: 1
  my.site  type MX  class IN  TTL 3600
  Preference: 10
  Mail Exchange: mail.my.site
```
После этого почтовый клиент делает дополнительный A-запрос для
`mail.my.site`, чтобы получить его IP-адрес.

---

### CNAME — каноническое имя (псевдоним)

Указывает, что запрошенное имя является псевдонимом другого имени.
Резолвер автоматически выполняет дополнительный запрос для целевого
имени, чтобы получить итоговый IP.

Пример записи:
```
www.my.site.  3600  IN  CNAME  my.site.
```
Ответ сервера на запрос A для www.my.site:
```
Transaction ID: 0xd4e5
Flags: 0x8180 (response, no error)
Answers: 2
  www.my.site  type CNAME  class IN  TTL 3600
    CNAME: my.site
  my.site      type A      class IN  TTL 3600
    Address: 192.168.100.1
```
Клиент получает оба RR: сначала CNAME-перенаправление, затем
финальный A-адрес — и соединяется с 192.168.100.1.
