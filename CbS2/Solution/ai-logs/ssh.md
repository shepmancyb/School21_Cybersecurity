> - Сессия 2 (пакеты #58–#131): настоящая SSH-сессия

## 1. Анализ TCP-рукопожатия перед SSH-сессией

**Вопрос AI:**
«Я смотрю на TCP-рукопожатие перед SSH-сессией в моём pcap. Объясни, какие
флаги установлены в каждом из трёх пакетов, и как происходит согласование
начальных sequence number. Сравни это с теоретическим описанием
трёхстороннего рукопожатия».

**Ответ:**

В `ssh.pcap` TCP-рукопожатие перед SSH-сессией — пакеты **#58, #59, #60**
(сессия с портом источника 15061 — это настоящее SSH-подключение с R2 на R1).

### Пакет #58 — SYN (клиент → сервер)

```
192.168.1.2:15061  →  192.168.1.1:22
Flags: S (SYN = 1, остальные = 0)
Sequence Number: 2544937994   ← случайный ISN клиента (R2)
Acknowledgment:  0            ← поле не используется, ACK = 0
```

Клиент (R2) инициирует соединение. Флаг `SYN` означает «синхронизирую
свой счётчик байт». Значение `2544937994` — это **Initial Sequence Number
(ISN)** клиента, выбранный псевдослучайно ядром операционной системы.
ACK-поле не заполнено, так как подтверждать ещё нечего.

### Пакет #59 — SYN-ACK (сервер → клиент)

```
192.168.1.1:22    →  192.168.1.2:15061
Flags: SA (SYN = 1, ACK = 1)
Sequence Number: 745060314    ← случайный ISN сервера (R1)
Acknowledgment:  2544937995   ← ISN клиента + 1 (подтверждение SYN)
```

Сервер (R1) одновременно делает два дела:
- Флаг `SYN` — объявляет собственный ISN `745060314` (независимый,
  выбранный Cisco IOS случайно).
- Флаг `ACK` — подтверждает SYN клиента: `2544937994 + 1 = 2544937995`.
  Прибавление единицы означает, что SYN «занял» один порядковый номер.

### Пакет #60 — ACK (клиент → сервер)

```
192.168.1.2:15061  →  192.168.1.1:22
Flags: A (ACK = 1, SYN = 0)
Sequence Number: 2544937995   ← ISN клиента + 1 (наш следующий байт)
Acknowledgment:  745060315    ← ISN сервера + 1 (подтверждение его SYN)
```

Клиент завершает рукопожатие — подтверждает SYN сервера: `745060314 + 1 =
745060315`. После этого пакета оба конца переходят в состояние
`ESTABLISHED`, и следующий пакет (#61) уже несёт прикладные данные —
баннер `SSH-2.0-Cisco-1.25\n` от сервера.

### Сравнение с теорией

Наблюдаемое поведение **полностью соответствует RFC 793**:

| Шаг | Теория | Наш дамп |
|-----|--------|----------|
| 1 | Клиент → SYN, ISN=X | #58: SYN, ISN=2544937994 |
| 2 | Сервер → SYN+ACK, ISN=Y, ACK=X+1 | #59: SYN-ACK, ISN=745060314, ACK=2544937995 |
| 3 | Клиент → ACK, ACK=Y+1 | #60: ACK, ACK=745060315 |

Оба ISN случайны и независимы — это защита от предсказания порядковых
номеров (TCP sequence prediction attack). Каждый флаг SYN и FIN «занимает»
ровно один порядковый номер, хотя реальных байт данных не несёт — именно
поэтому ACK всегда +1 к ISN.

## 2. Установление SSH-сессии и роль RSA-ключей

**Вопрос AI:**
«Я настроил SSH на Cisco с RSA-ключами (1024 бит). Посмотри на мой дамп
после TCP-handshake: там виден обмен версиями и начало шифрования. Какие
шаги включает установление SSH-соединения (алгоритмы key exchange, host key,
encryption)? Объясни, почему использование RSA-ключей важно для
предотвращения MITM».

**Ответ:**

После TCP-рукопожатия (пакеты #58–#60) в `ssh.pcap` видны следующие этапы:

### Этап 1 — Обмен версиями протокола (пакеты #61–#62, открытый текст)

```
#61  R1 → R2  "SSH-2.0-Cisco-1.25\n"       ← баннер сервера
#62  R2 → R1  "SSH-1.99-Cisco-1.25\n"      ← баннер клиента
```

Это единственный момент SSH-сессии, где данные передаются в открытом виде.
Именно эту строку мы и видели при проверке через `telnet 192.168.1.1 22` —
сервер отдал свой баннер и сразу закрыл соединение (пакет #45 с флагом FPA).

### Этап 2 — Согласование алгоритмов (SSH_MSG_KEXINIT, пакеты #63–#68)

Каждая сторона присылает список поддерживаемых алгоритмов (всё ещё до
включения шифрования, но уже в виде бинарных SSH-пакетов):
- **Key exchange**: `diffie-hellman-group1-sha1` / `diffie-hellman-group14-sha1`
- **Host key**: `ssh-rsa` (наш ключ, сгенерированный командой
  `crypto key generate rsa 1024`)
- **Encryption**: `aes128-cbc`, `3des-cbc` и др.
- **MAC**: `hmac-sha1`, `hmac-md5`
- **Compression**: `none`

Стороны выбирают первый совпадающий алгоритм из каждого списка.

### Этап 3 — Key Exchange (Diffie-Hellman) + подпись RSA (пакеты #65–#78)

Клиент и сервер выполняют DH: обмениваются открытыми значениями и
независимо вычисляют один и тот же **общий секрет**, не передавая его по
сети. Сервер подписывает результат обмена своим **приватным RSA-ключом**
и отправляет клиенту публичный host key + подпись. Клиент проверяет
подпись публичным ключом сервера — это доказывает, что на том конце
именно R1, а не злоумышленник.

### Этап 4 — SSH_MSG_NEWKEYS (пакет #76–#77)

Обе стороны отправляют `SSH_MSG_NEWKEYS` — сигнал «включаю шифрование».
Все пакеты начиная с #79 и далее в дампе — это **Encrypted packet**.
Содержимое (логин, пароль, команды, `exit`) полностью скрыто.

### Этап 5 — Аутентификация пользователя (внутри зашифрованного канала)

Логин `admin` и пароль проверяются уже внутри зашифрованного туннеля —
в дампе это выглядит как просто очередные зашифрованные пакеты между
#79 и #131. Перехватив трафик, узнать пароль невозможно.

### Почему RSA-ключ защищает от MITM

Diffie-Hellman даёт общий секрет, но не подтверждает *личность* сервера.
Атакующий посередине мог бы провести два независимых DH-обмена (один с
клиентом, другой с сервером) и подслушивать всё. RSA-подпись сервера
решает эту проблему: злоумышленник не знает приватный ключ R1, поэтому
не может подписать DH-данные так же, как это делает настоящий сервер.
Клиент, проверив подпись известным публичным ключом сервера, убеждается,
что говорит именно с R1, а не с посредником.

## 3. Сравнение Telnet и SSH по трафику в Wireshark

**Вопрос AI:**
«Чем отличается трафик Telnet и SSH в Wireshark? Я вижу, что после
TCP-подключения в SSH сразу идёт обмен версиями и зашифрованные пакеты.
Какие риски Telnet для безопасности сети?»

**Ответ:**

В `ssh.pcap` представлены оба типа трафика к порту 22:

**Сессия 1 (пакеты #27–#48) — `telnet 192.168.1.1 22`:**
- TCP handshake: #27 (SYN), #28 (SYN-ACK), #29 (ACK)
- Пакет #31: сервер сразу отдаёт баннер `SSH-2.0-Cisco-1.25\n` открытым текстом
- Пакет #44: клиент прислал мусорные байты `\r\n\x00\x00\x00\x00` — это
  Telnet-клиент, SSH-сервер его не понял
- Пакет #45: сервер закрывает соединение (флаг FPA = FIN+PSH+ACK)
- Итог: соединение разорвано, никакой аутентификации не было

**Сессия 2 (пакеты #58–#131) — настоящий `ssh -l admin 192.168.1.1`:**
- TCP handshake: #58 (SYN), #59 (SYN-ACK), #60 (ACK)
- #61: баннер сервера `SSH-2.0-Cisco-1.25\n`
- #62: баннер клиента `SSH-1.99-Cisco-1.25\n`
- #63–#78: согласование алгоритмов и key exchange (бинарные SSH-пакеты)
- #79 и далее: все пакеты — Encrypted, до самого #119 (FIN клиента)

### Итоговое сравнение

| Критерий | Telnet (как протокол управления) | SSH |
|---|---|---|
| Шифрование | Нет — всё в открытом тексте | Да — всё после NEWKEYS зашифровано |
| Что видно в дампе | Логин, пароль, команды, вывод устройства | Только баннер версии; дальше Encrypted packet |
| Аутентификация сервера | Нет — нельзя проверить, тот ли это узел | Да — RSA host key, проверяется подписью |
| Целостность данных | Нет отдельного механизма | HMAC на каждый пакет |
| Риск MITM | Критический | Минимальный (при проверке host key) |

**Риски Telnet для сетевой безопасности:** любой, кто перехватывает
трафик в том же сегменте сети (через ARP-спуфинг, port mirroring или
физический доступ к кабелю), получает учётные данные администратора и
полный контроль над устройством. Именно поэтому в задании настраивалось
`transport input ssh` на VTY-линиях — явный запрет Telnet для
подключения к управляющим интерфейсам маршрутизатора.
